# Tarello — дизайн-проект маркетплейса домашней еды

Дизайн-концепция мобильного приложения (p2p-маркетплейс домашней еды, по духу — Avito/Airbnb для еды), выполненная как статический веб-проект: интерактивный кликабельный прототип, UI-кит и карта пользовательских сценариев, готовые к передаче разработчикам.

> ⚠️ Важно: это **не готовое к продакшену приложение**, а дизайн-артефакт (замена Figma-файла). Функциональность (заказы, платежи, авторизация) не реализована как реальный бэкенд — это визуальная и интерактивная демонстрация UX-решений.

## Цель проекта

Спроектировать frontend мобильного приложения, где:
- **Покупатель** ищет и заказывает домашнюю еду у соседей рядом;
- **Повар** (любой человек) продаёт свои блюда без ресторана и аренды помещения;
- Центральная тема дизайна — **доверие** (незнакомому человеку платят за еду без ресторанной проверки), **гиперлокальность** и **живая ограниченность предложения** (порции, время готовности).

Визуальный язык — тёплый, «домашний», близкий по духу к Etsy/Airbnb, а не к типовым delivery-каталогам (Яндекс.Еда, Delivery Club, Uber Eats).

## Структура проекта / карта страниц

| Страница | Назначение |
|---|---|
| `index.html` | Лендинг-обзор: концепция продукта, сравнение ролей, навигация по остальным разделам |
| `flows.html` | Карта пользовательских сценариев (User Flow) для покупателя, повара, диаграмма переключения ролей, полный список экранов |
| `prototype.html` | **Интерактивный прототип** — все ключевые экраны в рамке телефона, с переключателем роли «Покупатель / Повар» и кликабельными переходами |
| `ui-kit.html` | UI-кит: цветовая палитра, типографика, кнопки, чипы, бейджи доверия/верификации, индикаторы статуса заказа, карточка блюда, иконография |
| `rationale.html` | Обоснование ключевых дизайн-решений — особенно про доверие и верификацию |

Тёмная тема переключается в правом верхнем углу любой страницы (кнопка ☀️/🌙) и сохраняется между страницами через `localStorage`.

## Экраны в интерактивном прототипе

**Покупатель:** онбординг (3 экрана) → лента/поиск с фильтром радиуса → профиль повара → карточка блюда → состояние «распродано» → оформление заказа → отслеживание заказа → профиль/настройки.

**Повар:** кабинет «Сегодня» → заказы (принять/готовлю/готово) → управление блюдами (вкл/выкл доступности) → добавление нового блюда (3 шага: фото/название → цена/порции → время готовности) → экран успешной публикации → профиль повара с верификацией.

Переключение роли — тумблер в сайдбаре прототипа (для демонстрации) и внутри самого приложения — блок «Стать поваром» / «Режим покупателя» в профиле (имитирует единый аккаунт без выхода из системы).

## Ключевые дизайн-решения (кратко, подробнее — `rationale.html`)

1. Профиль повара строится как личность (фото человека, история, специализация), а не как «точка продаж».
2. Детализированный рейтинг по 4 критериям (вкус, соответствие фото, упаковка, время) вместо общей «звёздочки».
3. Реальные UGC-фото от покупателей встроены в профиль повара и в отзывы.
4. Радиус поиска — крупный, видимый фильтр на главном экране, а не настройка в меню.
5. Живая доступность порций («осталось 3», «готово к 14:00», «распродано») с честной, не пугающей подачей состояния «распродано».
6. Тёплая палитра (терракот/шалфей/мёд/песочные нейтральные) и шрифт Fraunces для заголовков — уход от корпоративной эстетики delivery-приложений.
7. Кабинет повара без CRM-жаргона: крупные шаги, переключатели вместо календарей и таблиц.
8. Доступность: крупный базовый шрифт (15px), большие тап-зоны, поддержка тёмной темы.

## Данные и медиаконтент

- Весь текстовый контент (блюда, повара, отзывы, цены) — **демонстрационные моковые данные**, зашитые в `js/screens-data.js` для прототипа и напрямую в HTML для остальных страниц. Реальной базы данных / Table API в проекте не используется — это чисто фронтенд-дизайн-артефакт.
- Фотографии блюд и людей — подобраны через поиск изображений (реальные фото готовых блюд и людей на кухне/портреты), сохранены локально в `images/`. Используются как референс атмосферы и стиля для дизайна, не как финальные ассеты бренда.

## Структура файлов

```
index.html            — лендинг / обзор проекта
flows.html            — карта пользовательских сценариев
prototype.html        — интерактивный прототип приложения

  tokens.css          — дизайн-токены (цвет, типографика, тени, радиусы, тёмная тема)
  base.css            — общие стили сайта (хедер, кнопки, контейнеры)
  prototype.css       — стили экранов приложения внутри рамки телефона

  theme.js            — переключатель светлой/тёмной темы (общий для всех страниц)
  screens-data.js     — контент и разметка всех экранов прототипа
  prototype.js        — логика навигации, переключения ролей, интеракций прототипа
images/               — фотографии блюд, поваров, покупателей (для прототипа)
```

## Что не реализовано (и почему)

- **Реальные заказы, оплата, чат, push-уведомления** — прототип статический: все действия (добавление в корзину, «принять заказ», отправка формы) показывают тосты/переходы без сохранения состояния между сеансами.
- **Полноценная карта (Google/Yandex Maps)** — заменена стилизованной мини-картой-плейсхолдером; для реального приложения нужна интеграция карт-провайдера.
- **Верификация личности/самозанятости** — показана только как UI-статус; реальная верификация требует бэкенд-интеграции со сторонним KYC-сервисом (вне возможностей статического сайта).
- **Аналитика повара** — показаны только демонстрационные цифры; для реального продукта нужна отдельная бэкенд-аналитика.

## Рекомендуемые следующие шаги для разработки

1. Перенести компоненты UI-кита в дизайн-систему (Figma / код-компоненты) с реальными спецификациями отступов и состояний (hover/active/disabled).
2. Спроектировать и утвердить бэкенд-модель данных: пользователи, роли, блюда, заказы, отзывы, верификация, геолокация.
3. Добавить состояния ошибок и edge-cases (нет интернета, отказ повара от заказа, спор по заказу, возврат средств).
4. Провести юзабилити-тестирование формы добавления блюда с реальными представителями целевой аудитории поваров (в т.ч. старшего возраста).
5. Проработать нотификации (push) и их UX-паттерны для обеих ролей.
